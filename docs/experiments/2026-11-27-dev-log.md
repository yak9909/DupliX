## 4. GPU を温める試み（入れなかった）

- 案: フレームの作業の始めに、GPU に空回りの小さな処理（1 warp が `%globaltimer` を見て回る）を投げ、描画までにクロックを上げる。
- 注意: WDDM は投げた処理をためておき、次に待つまで送らない。投げた直後に `cuStreamQuery` しないと、空回りが描画の直前に走って描画を待たせる。
- 結果（AE なしの再生 `gpu_test`、3 秒休ませたあと）: 温めて 200 ms 待つと毎回 12〜13 ms。100〜150 ms では安定しない。
  空回りが続いている間に描くと（300 ms 温めて 100 ms 後）遅い回がある。AE の中では描画まで約 100 ms しかないので、
  フレームごとに温める方式では足りない。フレームの間も回し続けるのはドライバーの電源設定の真似で不確かなので、入れなかった（コードは戻した）。
- 代わり: 利用者に NVIDIA コントロールパネルで AfterFX.exe の電源管理を「パフォーマンス最大化を優先」にしてもらう。

## 5. 組の描画の「AE の行の前の準備」を縮めた（約 40 → 10〜15 ms、Test C）

- 調べ方: `RANDAMU_A3D_PROF=4`（組の描画の中だけを標本化）と、番地を関数名に直す PDB の読み取り（dbghelp。スクラッチパッドの `sym.py`）。
- 原因 1: 診断用の環境変数を毎回読んでいた（`OldMerge`・`GroupDrawOn`・`FrontBackGroupsOn`・`RANDAMU_A3D_DRAW`・`RANDAMU_MERGE_DRAFT`）。
  `GetEnvironmentVariableA` は AE の長い環境変数の一覧を先頭から探すので 1 回数 µs かかり、標本の約 18%。
  → `hook/env_cache.h` の `EnvCache`（最後に読んでから 250 ms は覚えた値。試験が `$.setenv` でレンダリングの合間に変える値も反映される）。
- 原因 2: `IsMine` → `LayerIsLive` が、comp の描画方式（`ArtisanIsCalder`／`ArtisanIsErnst`）を BEE に問うたびに AE の排他ロック（dvacore）を取る。
  コピーごとに約 6 回（`HookA3dDraw` 3 回、`HookTex` 3 回）。→ 描画の回の中で呼ばれるフック（不透明度・テクスチャ・範囲・ストリームの値・
  `HookA3dDraw`・奥行きの番号）だけ `IsMineInPass`（その回の間はレイヤーごとの答えを覚える。`ClosePass` で捨てる）。
  UI や次のフレームの準備（Count・Rects・IsLayerType など）は今までどおり毎回確かめる。
- 結果（Test C、3271 枚、CPU の段）: 組の描画の準備 40 → 10〜15 ms。ほかは計画 約 25、並べ替え 約 33、面の作成 約 6、行の処理 約 4、
  GPU の前の CPU 約 22（並べ替え 5、区間のまとめ 16）。
- 計測の注意: この時、AE 以外のプロセス（CUDA を使う python.exe と Android エミュレーター）が GPU を 100% 使っていて、GPU の段は
  1〜2 ms の処理が 230〜285 ms 待たされる回があった。GPU の時間はこの環境では当てにならない。

## 6. 大きい画像を複製すると重い（利用者の報告、11/27 4 時）

- 利用者: 「かなり速くなった。ただ 1920x1080 など大きな画像ファイルを複製対象にすると重い。GPU ならもっと速くできるはず」。
  NVIDIA の電源管理は「パフォーマンス最大化を優先」に変え済み、ほかのプロセスも GPU を使っていない。
- 試験の場面: `preview_setup.jsx` に `RANDAMU_PV_BIG`（画像のパス）を足した。`pv_bigS<n>` は複製元を差し替えて画面上の幅を元の
  花（217 px）に合わせて縮めたもの（テクスチャだけ大きい）、`pv_bigL<n>` は差し替えるだけ（画面上も大きい）。枚数は `RANDAMU_PV_COUNTS`。
  `RANDAMU_PV_BIG_MERGE=0` で軽量化オフ（AE が描く基準の絵）。画像は `tests/ae/make_big_png.py`（1920x1080、不透明、画素ごとに違う色）。
- 計測（Test C、画面の経路、1 フレーム）と原因:

| 変種 | 前 | 後 | 主な原因 |
|---|---|---|---|
| bigS380（組にならず 1 枚ずつ） | 1205 ms | 268 ms | テクスチャの比較 400 ms、GPU の並列度 |
| bigL380 | 937 ms | 389 ms | 同上 |
| bigS3271 の組の描画 | 約 900 ms | 60〜78 ms | 1 画素に数百枚が重なり、全部で縮小の平均を取っていた |
| 花 3271（Test C の既定） | 約 95 ms | 約 95〜115 ms | 変わらず（GPU の段は 16 → 19 ms） |

- 原因 1（テクスチャの比較）: `TexNoCopy` では全コピーに同じ master が渡るが、取り込むたびに `g_texGen++` するので `texKey` が毎回変わり、
  `AeSpansImpl` が 8 MB の `memcmp`（GPU 上の写しと同じか）をコピーごとにしていた。→ master ごとの通し番号（`SharedTex::serial`、
  `TexSerialOf`）を `texKey` にした。番地では判定しない（解放した master の番地に次の master ができることがある）。
- 原因 2（重なりの多い組）: 不透明な画素の下を飛ばす描き方（cull、11/26 に書いて既定オフ）は完全一致。→ テクスチャの不透明な画素
  （alpha 0xFF）の割合が 10% 以上なら自動でオン（`kCullOpaque`、`RANDAMU_GPU_CULL=0/1` で固定）。花は 0%（縁がぼけている）でオフのまま。
  閾値は切り抜きの画像（`make_big_png.py` の 4 番目の引数、楕円の内側だけ不透明）で決めた: bigS3271 の GPU の段が、不透明 50% で
  cull オフ 352 → オン 19 ms、78% で 352 → 7 ms。効かない時の損（花 16 → 24 ms）より効く時の得がずっと大きいので低くした（最初は 90%）。
  bigS3271 の GPU 816 → 9.6 ms。
- 原因 3（GPU の並列度）: タイル描きはスレッド 1 本で 8 画素を順に描くので、小さいコピー（数十行・数十画素幅）では働くスレッドが少なく、
  1 本が縮小の平均（1 画素に数十〜百画素）を 8 回続ける。→ スレッド 1 本で 1 画素の `AeSpanPixels`（8 画素ごとに保存した状態から同じ
  足し算で進める。絵はタイル描きと 1 ビットも違わない）。既定にした（`RANDAMU_GPU_PIXELS=0` でタイル描き）。
- 完全一致の確認: GPU の単体試験に不透明な 960x540 の場合を追加（`GpuAeBatch(300, 3, 960, 540, true)`）。cull 自動・固定オン ×
  画素ごと・8 画素ごとの 4 通りで CPU の基準と差 0。AE の中で画素ごと・8 画素ごとの絵が 24 フレーム一致。bigS380・bigL380 は軽量化オンと
  オフが 8 フレーム一致。
- 前からある差（今回の変更ではない）: bigS3271 は軽量化オンとオフで 9・12 画素（x 1073〜1086、y 460〜484、最大 56 段階）違う。
  変更前の版（30e09ec）でも同じ画素数で、変更前と変更後の絵は一致、cull オフでも同じ。**DupliX の組の描画が AE の描き方からずれる、
  前からある完全一致の不具合**（Test D は軽量化オン＝オフで本物のレイヤーと違った＝AE 自身の描き方。これはオン≠オフなので別物）。
  次の切り分け: `RANDAMU_GROUP=0`（組にしない）の絵とオフを比べる。差 0 なら組の順序の問題。軽量化オフは 3271 枚の 1920x1080 を描くのが遅すぎて（1 フレーム数秒）、bigL3271 は取れなかった。
- 残り（bigS3271、CPU）: AE の並べ替え（辺の作成）約 725 ms（対の判定 270 万回）、計画の対の判定 約 290 ms（候補 446 万対、重なり 158 万対）。
  花の 3271 枚（候補 75 万、重なり 5.6 万）よりコピー同士の重なりがずっと多い。380 枚（組にならない）は 1 枚ごとの GPU の往復が残る。

## 7. 組の中の塊を AE の M バッファーで描く（bigS3271 のオン≠オフ 9〜12 画素を修正）

- 利用者: 「不具合も残りの速さも全部やる。画素不一致は直せる場合絶対直す」。

  差の画素はすべてその穴の中、逆順に描くと差 0（この場面での偶然）。
- 原因: 塊は AE の `sub_180013470` が M バッファー（画素ごとの断片の一覧、解決するときに奥行きで並べる）に描くのに、

  代表の helper を待ち続けるため）。

  `sub_1800151F0`、仮想関数 3 番で描き先へ解決、仮想関数 0 番で削除。塊の前に溜めた GPU の仕事は先に流す。

## 8. CPU の残り（bigS3271、組 1 つ 3271 枚、重なる対 158 万）

- 計画の対の判定（`BuildIsolatedGroupPlan`）290 → 27 ms: 連結成分だけが要るので、スレッドごとの union-find で、すでにつながった
  対の重なりの判定を飛ばす（判定した対 158 万 → 1.5 万）。3D で交わるコピーの除外をやめた（組の中の塊は M バッファーで AE と同じに
  描けるようになったため）。
- AE の並べ替えの辺の作成（`BuildEdgesFast`）633 → 343〜388 ms、並べ替え全体 711 → 420〜484 ms:
  (1) 候補の対を 1 スレッドで集めてから判定していたのを、各スレッドが掃引の小分け（32 面ずつ取り合う）の中でその場で判定する形に。
  (2) 相手の一覧を数えて詰めてからスレッドで並べる。(3) 面ごとに一度だけ準備（頂点を詰めた配列、平面の商 a/c・b/c・d/c）した
  `AePairPrepared`。(4) 奥行きの差が 2 つの多角形を囲む四角の 4 隅で同じ符号に十分離れていれば、立ちうる印は 1 つなので、その印が
  立った時点で止める（AE の「両方立ったら止める」と同じ考え）。対の判定 385 → 212〜228 ms。
- この PC は i7-6700（4 コア 8 スレッド）。対の判定は 1 スレッド 1.37 秒、4 スレッド 0.50 秒、8 スレッド 0.39 秒（変更前）。
- 確認: 単体の対の判定の比較（AE 自身の `sub_18002B040` と）に準備した版を追加、200 万通りで差 0（最初の版は 2802 通り違った:
  標本が複数ある面で、前の標本で反対の印が立っていると自分の印を立てる前に止めていた。止める条件を「立ちうる側の印」に直した）。
  MERGE（`RANDAMU_GRAPH_CHECK=1`、AE の辺と突き合わせ 90 回以上で不一致 0）ALL PASS、EDIT ALL PASS、大きい画像のオン＝オフ 16 フレーム一致、
  Test〜D 各 8 フレーム差 0。
- 塊の描画の重さ: bigS3271 の組には塊が 28 個（面 57 枚）あり、AE の M バッファーで描く分（AE の CPU）に 200〜250 ms かかる。
  塊の修正（7 節）の前は DupliX の GPU で 1 枚ずつ描いていて速かったが、絵が違っていた。速くするには M バッファーへの書き込みと解決を
  同じ計算で再現する必要がある（未着手）。
- 組にならないコピーをまとめて描く案の注意（未着手）: 溜めている間に描き先に書くものの前で必ず流す。AE が自分で描く面、
  +129 の印の面の後処理 `sub_1800151F0`（`PF_DrawLine` で描き先に線を引く）、塊の M バッファーの解決、描き先の変化、フレームの終わり
