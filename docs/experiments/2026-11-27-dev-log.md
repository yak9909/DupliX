  345 枚以上で 1090 画素が誤って手前に出る）。軽量化オンもオフと差 0。詳細は HANDOFF.md の 11/27 0 時の節。
- 利用者の判断: AE と同じ絵のまま（気にしない）。
- 道具: `tests/ae/orbit_cut.jsx`（双子・部分集合・プロジェクトの保存）。

## 3. Test C（3271 枚）の内訳（画面の経路、`RANDAMU_A3D_TIME=2`、`RANDAMU_GPU_KTIME=1`）

| 段 | 時間 |
|---|---|
| 計画 | 約 25 ms |
| AE の並べ替え（辺の作成を含む） | 約 37 ms |
| AE の行の前の準備（コピーごとの状態・行の区間） | 約 40 ms |

| GPU の前の CPU（並べ替え 5〜7、区間のまとめ 17〜23） | 約 25〜34 ms |

- GPU が 2 通りに分かれるのは GPU のクロック（待機 345 MHz と最大 2100 MHz、約 6 倍）による。

## 4. GPU を温める試み（入れなかった）

- 案: フレームの作業の始めに、GPU に空回りの小さな処理（1 warp が `%globaltimer` を見て回る）を投げ、描画までにクロックを上げる。
- 注意: WDDM は投げた処理をためておき、次に待つまで送らない。投げた直後に `cuStreamQuery` しないと、空回りが描画の直前に走って描画を待たせる。
- 結果（AE なしの再生 `gpu_test`、3 秒休ませたあと）: 温めて 200 ms 待つと毎回 12〜13 ms。100〜150 ms では安定しない。
  空回りが続いている間に描くと（300 ms 温めて 100 ms 後）遅い回がある。AE の中では描画まで約 100 ms しかないので、
  フレームごとに温める方式では足りない。フレームの間も回し続けるのはドライバーの電源設定の真似で不確かなので、入れなかった（コードは戻した）。
- 代わり: 利用者に NVIDIA コントロールパネルで AfterFX.exe の電源管理を「パフォーマンス最大化を優先」にしてもらう。

## 5. 組の描画の「AE の行の前の準備」を縮めた（約 40 → 10〜15 ms、Test C）

- 調べ方: `RANDAMU_A3D_PROF=4`（組の描画の中だけを標本化）と、番地を関数名に直す PDB の読み取り（dbghelp。スクラッチパッドの `sym.py`）。
- 原因 1: 診断用の環境変数を毎回読んでいた（`OldMerge`・`GroupDrawOn`・`FrontBackGroupsOn`・`RANDAMU_A3D_DRAW`・`RANDAMU_MERGE_DRAFT`）。
  `GetEnvironmentVariableA` は AE の長い環境変数の一覧を先頭から探すので 1 回数 µs かかり、標本の約 18%。
  → `hook/env_cache.h` の `EnvCache`（最後に読んでから 250 ms は覚えた値。試験が `$.setenv` でレンダリングの合間に変える値も反映される）。
- 原因 2: `IsMine` → `LayerIsLive` が、comp の描画方式（`ArtisanIsCalder`／`ArtisanIsErnst`）を BEE に問うたびに AE の排他ロック（dvacore）を取る。
  コピーごとに約 6 回（`HookA3dDraw` 3 回、`HookTex` 3 回）。→ 描画の回の中で呼ばれるフック（不透明度・テクスチャ・範囲・ストリームの値・
  `HookA3dDraw`・奥行きの番号）だけ `IsMineInPass`（その回の間はレイヤーごとの答えを覚える。`ClosePass` で捨てる）。
  UI や次のフレームの準備（Count・Rects・IsLayerType など）は今までどおり毎回確かめる。
- 結果（Test C、3271 枚、CPU の段）: 組の描画の準備 40 → 10〜15 ms。ほかは計画 約 25、並べ替え 約 33、面の作成 約 6、行の処理 約 4、
  GPU の前の CPU 約 22（並べ替え 5、区間のまとめ 16）。
- 計測の注意: この時、AE 以外のプロセス（CUDA を使う python.exe と Android エミュレーター）が GPU を 100% 使っていて、GPU の段は
  1〜2 ms の処理が 230〜285 ms 待たされる回があった。GPU の時間はこの環境では当てにならない。
