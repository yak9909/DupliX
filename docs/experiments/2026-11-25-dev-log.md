## 2. 実装で分かったこと（Task 2〜5）

- ワールド変形の回転の順は、コピーと同じ `S·Rz·Ry·Rx`（行ベクトル）で AE のレイヤーの X/Y/Z 回転と一致した（`world_xform.jsx`、差 0）。
- 「ワールドの回転 × レイヤーの不均一な拡大縮小」はせん断になり、ワールド変形では正確に表せない（書き写しは近似）。
- スクリプトで親子付けすると、AE は子のワールドの向きを保つように子の方向を変える。試験では親子付けのあとに方向を 0 に戻す。
- 2D にしたレイヤーの位置・拡大縮小は、スクリプトでは 3 成分のまま読める（z は使われない）。
- 高速モードをオンにした時点の 2D の位置のずれも、書き写しでワールド変形に入る（試験 `fast_move2d` は、オンにしたあとで動かす）。
- 利用者のシーン（`run_as_is.ps1`、`run_orbit_order.ps1 -Deg 26`）は新しい高速モードで合格（高速と通常の差の平均 0.6）。軌道のアニメーションを 120 フレーム比べる試験は、親のアニメーションを写さない決定により前提がなくなった（角度を固定した 1 フレームだけ有効）。

## 4. 実装中の判断と最終レビュー

計画からずらした判断（実装者が決めたもの）:
- ワールド変形の回転の順は計画の書き方（Rx·Ry·Rz）ではなく、コピーと同じ `S·Rz·Ry·Rx`（AE と一致を確認）。
- ワールド変形の位置はレイヤーの座標でのずらしなので、レイヤーの拡大縮小が掛かる。
- `PlaneM4`・`AnchorDepth` は製品では使わなくなったが、`CopyHomography` の単体テストの準備に使うので残した。
- 試験の作りの修正: `fast_move2d` は奥のレイヤーのない双子のコンプと比べ、高速モードをオンにしたあとで動かす。`fast_remove` の比較先は同じ 2D レイヤー。`world_xform` は `saveFrameToPng` で描く。利用者のシーンの前後の絵は `run_as_is` のものを使い、`run_orbit_order` は `-Deg 26` だけ。
- `TransferLayerToWorld` は `params[]` を受け取らず、今のワールド変形を受け取って新しい値を返す（書き込みは呼び出し側）。

最終レビュー（別のレビュー役、Critical なし）で直したもの:
- 位置の次元が分割されていると、途中で失敗してレイヤーが半分だけ初期化されていた → 何も変える前に確かめて止める（`toggle_separated`）。
- ワールド変形にキーフレームがあると、`params[]` への書き込みはその時刻にキーフレームを 1 つ足すだけで、ほかのキーフレームが正しく写らない（AE で確認: 2 個 → 3 個）→ レイヤーが初期状態でないときは止めて「状態」で案内し、初期状態なら何も書かない（`toggle_world_keys`、`toggle_initial_keys`）。
- 途中で一部の設定に失敗したときも、ワールド変形は書く（Partial）。「写せませんでした」の案内が出ていなかったのも直した。
- カメラだけが動く場合にキャッシュが古い絵を返さないか → 試験 `fast_camonly` を足し、問題なし（修正不要）。
- このレイヤーを親にしているほかのレイヤーが一緒に動く件 → 手引きに書いた（自動で補正するには別の実験が要る）。

後回しにした軽微な指摘:
- 高速モードの前処理は毎回パラメータを読み、登録の世代を進める（もともと描画ごとに進めているので影響は小さい）。
- 「状態」の案内の記録（`g_transferNote`）は、エフェクトの削除や取り消しでは消えない。登録が失敗したときに前のレイヤーの鍵に付くことがある。
- 11/24 の高速モードで保存したプロジェクト（高速モードがオンの 3D レイヤー）は、開くと絵がずれて見える（「状態」は 2D にするよう案内する）。
- 取り消しのあと、シーケンスデータの中のワールド変形の写しが古いまま残る（読み込み直後の最初の描画まで）。
- アンカーポイントにアニメーションがあると、書き写しの時刻以外で少しずれる。
- 計画の `max_result_rect` の丸め（計画は ceil、実装は左上を floor）。

## 5. 高速モードの GPU 化と CPU 版の軽量化（計画 `docs/superpowers/plans/2026-11-25-fast-mode-gpu.md`）

- **Furikake は GPU で描いていない**（取り込みに CUDA・OpenCL・DirectX がなく、描画の部品は `RenderCPU::DrawZBuffer` などの CPU 版だけ）。速さは CPU の Z バッファによるとみられる。randamu は見た目を変えない方式（画素ごとの奥行きで並べて合成）のまま速くした。
- 時間の内訳（利用者のシーン、aerender の MFR オフ、GPU 対応前）: 高速モード 100 枚で 1 フレーム 510〜540 ms のほぼ全部が randamu の描画（`SmartRender`）。
- CPU 版: 画面を 16×16 の区画に分け、コピーを手前の点の近い順に処理し、不透明なかけらより奥は計算しない（結果は同じ。比較用の旧版 `raster_ref.cpp` と差 0）。1 画素のかけらは 64 まで（超えた分は一番遠いものを奥の溜めに回す）。単体の目安（1920×1080、不透明な切り抜き 577×680、8 スレッド）: 10 枚 12.5→11.5 ms、100 枚 85→45 ms、1000 枚 830→60 ms。
- GPU 版: CUDA のカーネル（`src/gpu/fast_raster.cu`）を CUDA 12.2 の `nvcc -ptx`（compute_52）で PTX にしてプラグインに埋め込み、`nvcuda.dll` のドライバー API で読み込む。VS 2022 の STL は CUDA 12.4 未満を拒むので `-D_ALLOW_COMPILER_AND_STL_VERSION_MISMATCH`（カーネルは STL を使わない）。単体（自前の文脈）: 10 枚 1.4 ms、100 枚 2.2 ms、1000 枚 14 ms、1 万枚 117 ms（一覧の転送込み）。
- AE の GPU の絵は BGRA の float（`float4` の x=B … w=A）、行の長さは rowbytes/16 画素、ストレートアルファ（SDK の見本どおり。AE の試験で CPU 版と一致を確認）。
- GPU と CPU の差: randamu の描画は平均 0.0003 以下・最大 1（8 ビット）。GPU は奥行きを float で比べるので、ほぼ同じ奥行きのコピー同士はごく一部の画素で前後が入れ替わる（単体の 20 場面で 0.0001% の画素）。1/2 解像度（平均 6.3）と GPU のドロップシャドウ（0.15）は、通常モードでも同じだけ違う＝ AE 自身の GPU と CPU の違い。
- 利用者のシーン（書き出し、MFR オフ、1 フレーム）: 通常 10 枚 183 ms。高速 CUDA 10/100/1000 枚 = 約 50/50/117 ms、高速 CPU = 約 100/133/333 ms（対応前 117/570/10 秒以上）。
- 試験: `pwsh tools/build.ps1 -Target gpu; build/gpu/gpu_test.exe`（GPU ALL PASS）、`pwsh tests/ae/run_fast_mode.ps1`（CPU）のあと `pwsh tests/ae/run_fast_mode.ps1 -Gpu CUDA`（GPU の経路を使ったことと、CPU の結果との一致）、`-Gpu CUDA -SkipScene -GpuFail`（GPU の失敗時に CPU で描き直す）。利用者のシーンの GPU 設定は `RANDAMU_USER_GPU=SOFTWARE|CUDA` で上書きして測れる（`run_user.ps1`）。
- 実装中の判断（計画からの逸脱を含む）: 区画の一覧と 64 枚の上限は CPU と GPU で同じ規則（手前から処理、不透明の奥は捨てる、超えたら一番遠いものを奥の溜めへ）。区画は 16×16（行の帯ではなく）、作業領域は使い回す。GPU の絵の形式は SDK の見本に従い、捨てる実験はせず AE の試験で確かめた。`gpu_raster` は `src/gpu`（AE に依存しない）。nvcc 12.2 には STL の版の不一致を許す指定が要る。GPU と CPU の比較は最大値ではなく平均と 2 段階を超える画素の割合で判定（float の奥行きでほぼ同じ奥行きの前後が入れ替わるため）。AE の GPU と CPU の差は、通常モードでの AE 自身の差と比べて判定。`fast_gpu_switch` は `saveFrameToPng` を使うので GPU の経路を通らない可能性がある（この試験が証明する範囲は狭い）。
- **最終レビュー（11/25 午後、判定「修正すれば統合してよい」）で直したもの**（commit c6fe738）: (1) GPU で描けないときに CPU で描き直さなかった → AE の GPU の描画の中で、絵を CPU に移して CPU 版で描き、GPU に戻す。カーネルの読み込みや起動の失敗は以後ずっと覚えて、次のフレームから GPU を使わない。(2) PTX（ISA 8.2）は R535 以降のドライバーが必要 → GPU の準備（`GPU_DEVICE_SETUP`）でカーネルを読み込み、失敗なら CPU。手引きに必要なドライバーを書いた。(3) 文脈ごとのカーネルを消さなかった → `GPU_DEVICE_SETDOWN` で消す。(4) 大きな仕事を 1 回の起動で描き、止められなかった → 区画 8 行ずつの帯で起動し、その間に AE の中止を確かめる。一覧が 3200 万件を超えたら CPU。(5) 区画の一覧の件数が int であふれ得た → 64 ビットで先に数え、2^28 件を超えたらメモリ不足として止める。
- 後回しにした軽微な指摘: GPU のメモリを AE のメモリ管理を通さず毎フレーム確保している、1 スレッドあたり 1.5 KB のローカルメモリ、64 枚を超えたときの追い出しは入ってくるかけらが一番遠くても残す（ごく薄いコピーが 64 枚を超えて重なるときだけ見える。手引きの「手前の 64 枚までは正確」は少し言い過ぎ）、作業スレッドでのメモリ不足は AE を落とす、`raster.cpp` の注記の大きさ（1.5 MB ではなく約 0.5 MB）、作業領域を最大 64 個まで持ち続ける、1/2 解像度で負の原点の GPU の単体試験がない、GPU の描画のエラーコードがすべて同じ値になる、新しく取ってきたリポジトリで msbuild だけでは作れない（PTX のヘッダーは build.ps1 が作る）。

- **後回しにした軽微な指摘を直した（11/25 午後、利用者の指示）**: GPU の一覧のメモリは AE の `PF_GPUDeviceSuite1::AllocateDeviceMemory` で確保（`GpuAllocator`。単体の試験で確保と解放の数が一致）。64 枚を超えたときは、入ってくるかけらが一番遠いとき、または奥の溜めにあるものより遠いときは奥の溜めの下に回す（遠いものが近いものの上に来ない。`raster_overflow_order`・`gpu_overflow_order`、修正前は差 0.00026 と 0.0051）。作業スレッドのメモリ不足は、そのスレッドだけ止めて呼び出し元が残りを描く（`raster_worker_out_of_memory`、修正前は試験のプロセスが異常終了）。作業領域の保持はハードウェアのスレッド数の 2 倍まで、注記を約 0.5 MB に訂正。1/2 解像度で負の原点の GPU の単体試験（`gpu_origin_half`）。GPU の描画で AE の関数のエラーはそのまま返す。PTX のヘッダーがなければ msbuild が作る（vcxproj の `RandamuPtx`）。手引きの 64 枚の説明を直した。
- 直さなかったもの: カーネルの 1 スレッドあたり 1.5 KB のローカルメモリ（64 枚分の色・奥行き・順位）。減らすには 64 枚の上限か精度を変える必要があり、CPU と同じ規則が崩れる。RTX 3060 で約 66 MB（1536 B × 同時に動くスレッド数）で、AE の GPU メモリに対して小さいので、このままにした。

## 5b. まとめる軽量化の実験（11/25 午後、使い捨て。差分は `spike/atlas/texture_swap_spike.patch`）

目的: 通常モードで、群れを 1 枚の絵にした「群れの面」を AE に描かせられるか。まとめないコピーは本物と画素一致のままか。

- **`GetSubLayerRects` の矩形と M3 は、AV レイヤーの絵に効かない。** エフェクトの出力を右に広げる（元の絵＋色を反転した絵）と、矩形が元のまま（`0 0 120 100`、並びは左・上・右・下）でも、全部のコピーに広げた絵全体が写った。矩形や M3 を変えても絵は変わらない。
- **AE の 3D 描画は、コピー 1 枚ごとに AEGPDriver の `AEGP_RenderTexture`（中身は `BEE_RenderTextureForArtisan`）で絵を受け取る。** 引数の RenderTrace から、レイヤーとコピーの番号が分かる（不透明度のフックと同じ）。戻りは絵（`AEGP_WorldH`＝内部の `PF_World*`。`PF_EffectWorld` とは並びが違う）と M3（絵の画素→レイヤーの画素、行ベクトル形式）。絵はレイヤーの範囲（エフェクトの出力の範囲）で切り取られる。使い終わった絵は `AEGP_DisposeTexture` で返され、その中身は仮想デストラクタで `delete` するだけ（`spike/ida/dump_table`）。`...WithReceipt` 版は、書き出し・画面・影ありのどれでも呼ばれなかった。
- **方式 A（並べた絵＋引き伸ばし）は不採用。** 出力に絵を並べ、M3 で選ぶ部分をレイヤーの範囲いっぱいに引き伸ばし、M4 で縮め戻すと、選んだ部分だけが写る。絵と絵の間に透明な隙間（8 画素以上。4 画素ではにじんだ）があれば、正解比較の一式の大半が差 0 になった。しかし拡大して写るコピーの縁で差が出た（`layer_xform` 最大 3、`count100` 最大 5。倍率を 4 にすると最大 7）。AE がレイヤーの縁をレイヤーの画素の単位でぼかすためとみられ、まとめないコピーまで本物と一致しなくなる。
- **方式 B（絵の差し替え）を採用候補にした。** エフェクトの出力は元のまま。群れの面のコピーだけ、`BEE_RenderTextureForArtisan` の戻りの絵を、公開の `AEGP_WorldSuite3::AEGP_New` で作った自前の絵に差し替える（元の絵は `delete` する。自前の絵は AE が `AEGP_DisposeTexture` で `delete` する）。結果: 差し替えたコピーだけが変わり、ほかのコピーは差 0（手を加えないので一致は構造上の保証）。2 倍の大きさの絵を M3 で縮めて渡しても同じ絵（差 0）。書き出し（MFR オフ）と UI の試験（`run_ui.ps1`、画面で 34 回差し替え）で、落ちず、画面と書き出しが一致。
- 未確認: MFR オン、GPU 設定（CUDA）、16・32 bpc の絵、1/2 解像度での絵の解像度、モーションブラーのときの呼ばれ方、`...WithReceipt` が使われる場面。
