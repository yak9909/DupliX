- レンダーキュー（前日の計測で花の分 15〜30 ms）と画面がこれほど違ったのは、下の 2 つの処理が画面の経路でだけコピーごとに起きていたため。

## 2. 分かったこと（画面の経路、Test A、軽量化オフ、1 枚あたり）

| 内訳 | 時間 | 根拠 |
|---|---|---|
| AE がコピーごとにテクスチャを取り直す（レイヤーの描画の流れ全体: エフェクトの前処理・キャッシュの確認など） | 約 1 ms | `RANDAMU_A3D_DRAW=4`（画素なし）と `=2`（描画なし）の差。380 枚: 577 対 203 ms |
| 不透明度のフックでの AEGP の読み直し | 約 0.55 ms | `prof:` の行で Opacity 8192 回に対して AEGP read 8685 回 |
| テクスチャのフック（以前の群れの方式の `SwapGroupTexture`）での AEGP の読み直し | 約 0.9 ms（オンだけ） | 簡易プロファイラーで `bee_hooks.cpp` の `ReadParamsFromEffect` が最多 |
| 画素の計算（AE） | 0.17〜0.35 ms | `=4` と通常の差。小さい花なので軽い |
| DupliX の GPU の往復（オン） | 約 1 ms | `RANDAMU_A3D_TIME=1` の `gpu-call` |

- 不透明度のフックのキャッシュが毎回外れた理由: エフェクトの SMART_PRE_RENDER はサブレイヤーごとに 1〜2 回来る（380 枚で 761 回）。その早道で毎回 `RegTouch()`（世代を進める）していたため。
- 全コピーのテクスチャは同じ中身（ハッシュ・大きさ・行列が一致、`a3d tex args` の記録）。
- スクリプトでの編集（`setValue`）では、エフェクトに描画以外のコマンドは届かない（`RANDAMU_CMDLOG=1` で確認）。編集を知る手がかりは描画のときの PreRender だけ。
- 既定のビルドが Debug だった（`tools/build.ps1`）。利用者が試していたのもデバッグ版。ただし Release にしても速さはほぼ同じ（重さは AE の関数の側）。

## 3. 修正（commit 2bbac0d）

1. `SwapGroupTexture` は以前の方式（`RANDAMU_MERGE_OLD=1`）のときだけ動く。
2. PreRender の早道では、パラメーター（`PF_CHECKOUT_PARAM`）とアンカーの指紋が、同じレイヤー・時刻の前回の指紋と違うとき（または初めての時刻）だけ世代を進める（`ParamsChangedAt`、`randamu.cpp`）。
3. 軽量化がオンのレイヤーは、1 フレームの描画の中で同じ要求（描画の文脈・レイヤー・ヒント・倍率・範囲）のテクスチャを 2 枚目以降は 1 枚目の複製で返す（`HookTex`、`AEGP_New` の世界を AE が破棄する）。範囲は `HookA3dDraw` の中だけで、描いた面の数（ctx+252）が 0 のときと全部描き終えたときに捨てる。
4. `tools/build.ps1` の既定を Release にした。

## 6. 診断の道具（環境変数）

- `RANDAMU_A3D_TIME=1`: コピーごとの時間（準備・反復・GPU の内訳）、テクスチャの要求の中身（`a3d tex args`、64 px 以上）、SAT の作成と AE の補助関数の時間。
- `RANDAMU_A3D_PROF=1`（コピーの描画の準備の間）/ `=2`（描画のスレッドをずっと）: 簡易プロファイラー。約 50 µs ごとに命令の位置とスタックを取り、モジュールの連なり・Advanced3D と randamu の戻り先ごとに数えて 1000 件ごとにログへ。randamu の位置は `spike/tools/sym_pdb.py`（dbghelp で pdb を引く）で関数と行にした。
- `RANDAMU_A3D_AEPIX=1`: テクスチャは共有し、画素は AE が描く。
- `RANDAMU_CMDLOG=1`: エフェクトに届くコマンドをすべて記録。

## 8. 続き（11/26 午前、利用者「残りの軽量化も進めてください」）

利用者が画面で同じ結果を確かめたうえで、残りの軽量化を依頼。

| 変更 | 中身 | 効果（画面の経路、Test A） |
|---|---|---|
| レイヤーの範囲の共有 | Advanced3D は描く前にサブレイヤーごとに `AEGP_GetRenderLayerBounds`（Canvas Suite 版 10 の 16 番、`sub_180008710`）を問い、そのたびに DupliX の PreRender（＋編集検出の指紋）が走る（1 回 約 0.35 ms）。軽量化がオンのレイヤーは、1 回の描画の準備（同じスレッドの `AEGP_GetNumLayersToRender`＝版 10 の 1 番から次まで）の中で、同じレンダーコンテキスト・レイヤー・時刻の 2 回目以降に 1 回目の答えを返す（`HookGetBounds`） | 100 枚 57→46 ms、380 枚 237→165 ms。PreRender は 1 フレーム 約 100 回→3 回 |
| GPU への絵の再転送を省く | 前回送った絵の控え（CPU 側）と、各行の画素の部分が完全に同じなら送らない（`GpuAeSpans`。行の余白は絵ごとに違うので比べない） | 380 枚 165→110 ms 前後 |

- 範囲の答えが全コピーで同じことの確認: `RANDAMU_BOUNDS_SHARE=0 RANDAMU_A3D_TIME=1` で、2 回目以降の答えを 1 回目と比べ、792 回すべて同じ（0 0 216 217）。

### 8b. 組の方式の検討とストリームの値の共有（11/26 昼）

- 利用者の案: 他の絵と交わらないコピーを一枚絵にまとめる（手前・奥の組に分ける）。以前の方式のコード（`merge_plan`・`ae_order`・Count/Rects の群れの面）を流用できる。新しく要るのは、組の中のコピーを AE と同じ計算でフレームへ直接描くための、コピーごとの描画の行列と行の範囲を AE と完全に同じに作ること。
- 上限の計測（画面の経路、Test A）: 画素を描かない（`RANDAMU_A3D_DRAW=2`）とそのままで差がない（380 枚 85〜97 ms どうし）。残りは AE がサブレイヤーごとに行う準備。コピー 1 枚の変種 `pv_on1` は約 10 ms。
- 範囲の問い合わせ（`sub_180008710`）の中で、Advanced3D はサブレイヤーごとに Stream Suite（版 7、+128＝`AEGP_GetLayerStreamValue`）でレイヤーの拡大縮小（2）と素材の設定（22〜30）を読む（`sub_18000ABB0`・`sub_18000A6C0`）。軽量化オンのレイヤーは、1 回の描画の準備の中で同じ問いに 1 回目の値を返す（`HookLayerStreamValue`、版 7 の表の 16 番）。2000 回すべて 1 回目と同じ値であることを確認（`RANDAMU_BOUNDS_SHARE=0`）。
- 結果: 100 枚 41→29〜33 ms、380 枚 131→85〜101 ms。オン＝オフ（4 種類）差 0、EDIT・MERGE・利用者のシーン・REF・UI 合格。
- 簡易プロファイラー（`RANDAMU_A3D_PROF=3`＝1 回の描画の準備から最後の面まで）は GPU の同期待ちを大きく見せる（止めて調べる方式が待ちを延ばすとみられる）。描画の費用は DRAW=2 との差で測る。
- 計測のスクリプトが届かない件の原因: AE の警告「1 つのスクリプトを実行中に 2 つめを実行しようとしたため、2 つめは実行されませんでした」（題名のない `#32770`、文字は `WM_GETTEXT` で読めた）。準備のスクリプトが結果のファイルを書いてから終わるまでの間に送っていた。`run_preview.ps1` は準備のあと 5 秒待ち、届かなければ送り直し、この警告は閉じる。各スクリプトは最初に `script_got.txt` を書き、すでにあれば何もしない。
- 計測用のコピーのプロジェクトでは、元のコンポの DupliX のレイヤーを無効にする（隠れた AE が裏で描く分を減らす。起動時の 1 回は残る）。
- 残りの候補: 不透明度の問い合わせ（`sub_18000A6C0` の Canvas Suite +136）の共有、フックの時間（380 枚で約 20 ms）、GPU の往復を連続するコピーでまとめる（1 枚 約 0.4 ms の同期待ち。AE の描画の途中に AE が直接描く経路（`sub_1800149A0`、塊の合成）があるので、まとめるなら区切りの見極めが要る）。
