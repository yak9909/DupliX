## 2. 分かったこと（画面の経路、Test A、軽量化オフ、1 枚あたり）

| 内訳 | 時間 | 根拠 |
|---|---|---|
| AE がコピーごとにテクスチャを取り直す（レイヤーの描画の流れ全体: エフェクトの前処理・キャッシュの確認など） | 約 1 ms | `RANDAMU_A3D_DRAW=4`（画素なし）と `=2`（描画なし）の差。380 枚: 577 対 203 ms |
| 不透明度のフックでの AEGP の読み直し | 約 0.55 ms | `prof:` の行で Opacity 8192 回に対して AEGP read 8685 回 |
| テクスチャのフック（以前の群れの方式の `SwapGroupTexture`）での AEGP の読み直し | 約 0.9 ms（オンだけ） | 簡易プロファイラーで `bee_hooks.cpp` の `ReadParamsFromEffect` が最多 |
| 画素の計算（AE） | 0.17〜0.35 ms | `=4` と通常の差。小さい花なので軽い |
| DupliX の GPU の往復（オン） | 約 1 ms | `RANDAMU_A3D_TIME=1` の `gpu-call` |

- 不透明度のフックのキャッシュが毎回外れた理由: エフェクトの SMART_PRE_RENDER はサブレイヤーごとに 1〜2 回来る（380 枚で 761 回）。その早道で毎回 `RegTouch()`（世代を進める）していたため。
- 全コピーのテクスチャは同じ中身（ハッシュ・大きさ・行列が一致、`a3d tex args` の記録）。
- スクリプトでの編集（`setValue`）では、エフェクトに描画以外のコマンドは届かない（`RANDAMU_CMDLOG=1` で確認）。編集を知る手がかりは描画のときの PreRender だけ。
- 既定のビルドが Debug だった（`tools/build.ps1`）。利用者が試していたのもデバッグ版。ただし Release にしても速さはほぼ同じ（重さは AE の関数の側）。

## 3. 修正（commit 2bbac0d）

1. `SwapGroupTexture` は以前の方式（`RANDAMU_MERGE_OLD=1`）のときだけ動く。
2. PreRender の早道では、パラメーター（`PF_CHECKOUT_PARAM`）とアンカーの指紋が、同じレイヤー・時刻の前回の指紋と違うとき（または初めての時刻）だけ世代を進める（`ParamsChangedAt`、`randamu.cpp`）。
3. 軽量化がオンのレイヤーは、1 フレームの描画の中で同じ要求（描画の文脈・レイヤー・ヒント・倍率・範囲）のテクスチャを 2 枚目以降は 1 枚目の複製で返す（`HookTex`、`AEGP_New` の世界を AE が破棄する）。範囲は `HookA3dDraw` の中だけで、描いた面の数（ctx+252）が 0 のときと全部描き終えたときに捨てる。
4. `tools/build.ps1` の既定を Release にした。

## 6. 診断の道具（環境変数）

- `RANDAMU_A3D_TIME=1`: コピーごとの時間（準備・反復・GPU の内訳）、テクスチャの要求の中身（`a3d tex args`、64 px 以上）、SAT の作成と AE の補助関数の時間。
- `RANDAMU_A3D_PROF=1`（コピーの描画の準備の間）/ `=2`（描画のスレッドをずっと）: 簡易プロファイラー。約 50 µs ごとに命令の位置とスタックを取り、モジュールの連なり・Advanced3D と randamu の戻り先ごとに数えて 1000 件ごとにログへ。randamu の位置は `spike/tools/sym_pdb.py`（dbghelp で pdb を引く）で関数と行にした。
- `RANDAMU_A3D_AEPIX=1`: テクスチャは共有し、画素は AE が描く。
- `RANDAMU_CMDLOG=1`: エフェクトに届くコマンドをすべて記録。

### 8c. 組の描画（11/26 午後、利用者「組の方式に取り掛かってください」）

- **仕組み:** 他と重ならないコピーをレイヤーの組にまとめ、AE にはサブレイヤー 1 枚（組の中で画面上が一番大きいコピー＝代表）として渡す。AE が代表を描く時に、組の全部のコピーを AE 自身の関数で「サブレイヤーだった場合と同じに」描く。
  - 組分け `BuildIsolatedGroupPlan`（`merge_plan.cpp`）: コピーの画面上の四角（余白 3 px）が、他のレイヤー・他のレイヤーのコピーと重ならず、3D で交わるコピーを含まない成分（重なりのつながり）。カメラの後ろに出るコピーがあるレイヤーは組にしない。
  - レイヤーごとのデータ（`ctx[0]+432`、1 件 192 バイト、`sub_180008710` が作る）を代表から写し、ワールド行列（コピーの行列 × レイヤーの行列を U.dll の `M_Matrix4::operator*=` で。`RANDAMU_XF_CHECK=1` で BEE の値と 512 回ビット一致）と不透明度（AE の値 × コピーの値）と奥行きの補正の番号（`+0x34`）だけ差し替える。`+0x30`（テクスチャと描画のパラメーターのレイヤー番号）は代表のまま（変えると AE が例外 3 を投げた）。
  - 面は `sub_1800159A0`（`sub_180013160` と同じ初期化と引数）、並べ方は `sub_18002AA00`（AE の確保 `sub_18005FD58`・解放 `j_j_free` でリストを作る）、`sub_1800127B0`、描画は `sub_180014800` の中身をなぞる（`sub_180050FD0` で描画のパラメーター → 面の vtable の描画）。`sub_180014800` をそのまま呼ぶと BEE の補助オブジェクトを二重に作る形になり、AE の描画が止まった（実際の原因は上の例外 3 だった可能性もある）。
  - 奥行きの補正の番号: 組を作るとサブレイヤーが減って後ろの番号が詰まり、家と交わるコピーの交線が 1 画素ずれた（細い縦の筋、最大 197）。`sub_180008710` が各データの最後に呼ぶ `AEGP_GetLayerIndex`（Layer Suite 版 10、出力先 = データ + 176）のフック `HookGetLayerIndex` で、`+0x34` を組なしの番号に戻す。
  - GPU: 組の間はコピーごとの行と状態をため（`t_groupJobs`）、組の終わりにまとめて描く（`GpuAeSpansBatch`）。行の区間を行ごとに合わせて詰めて送り（`AeSpanRowsPacked`）、重なりの「段」ごとに 1 回の命令。テクスチャの画素は DupliX 側に写して持つ（AE は各面の描画の終わりにテクスチャを手放すので、ポインターのままだと後で解放済みの領域を読んで絵が崩れた）。AE が自分で描くコピー（条件の外）の前には、ためた分を先に描く。
- **結果（画面の経路、span）:** Test.aep 100 枚（全部が組）38.6 → 22.2 ms。Test A: 20 / 100 / 380 枚 = 14 / 23 / 144 ms（380 枚は 1 フレームの外れ値 394 ms を含む。密集していて組は 2 枚だけ）。オフと全部差 0。
- **試験（組を有効にして）:** EDIT ALL PASS、MERGE ALL PASS（234 本の記録のうち 72 本で組を描いた。16/32 bit・MFR オンを含む）、利用者のシーン（Test A・Test）オン＝オフ、REF・UI・単体・GPU 合格。
- **既定で有効**（`RANDAMU_GROUP=0` で止める）。
- **注意（穴）:** 代表の描画で組の描画が断られる場合（描き込み先の種類が 1 以外＝塊に入った、動きのぼかし）は、組の他のコピーが描かれない。組分けで重なりのないコピーだけにしているので塊には入らないはずで、動きのぼかしはレイヤーの理由（block）で組にしない。断られた時はログ「group: not drawn as a group」が出る。
- **次の候補:** 手前・奥の組（家と重なっても、はっきり手前か奥にあるコピー）。密集した場面（Test A の 380 枚）はつながりで全部が家に届くので、今の組分けでは効かない。

### 8d. 手前・奥の組（11/26 夕方、利用者「次の段階の手前、奥のまとめを実装して」）

- **仕組み:** レイヤーごとに組を最大 2 つ作る。手前の組はフレームの全部の面のあとに、奥の組は全部の面の前に描く。組の各コピーは、画面で重なる組の外の面（他のレイヤー、他のレイヤーのコピーと組、1 枚ずつ描くコピー）すべてより、はっきり手前（奥）にある。だから描く位置を最後（最初）に動かしても、重なる面との前後は AE の順と同じになる。他と重ならないコピーは手前の組に入る。
  - 組分け `BuildFrontBackGroupPlan`（`merge_plan.cpp`）: 対の判定は 3 通り。(a) 余白 3 px を足しても離れている → 関係なし。(b) 重なりがあり、余白を足した四角どうしの重なりの多角形の頂点すべてで奥行きの差が同じ向き（相対 1e-5 より大きい）→ 手前・奥が決まる（平面なので 1/z は画面上で 1 次式。凸の重なりは頂点で決まる）。(c) それ以外（余白の帯の中だけで重なる、交わる、同じ奥行き、カメラの後ろ）→ あいまい。あいまいな対を持つコピーは組にしない。条件を満たさないコピーを外すことを、外すものがなくなるまで繰り返す（外れたコピーは同じレイヤーの組のコピーにとって「外」になり、もう一度調べる）。手前を先に決め、残りで奥を決める。
  - AE の対の判定（`sub_18002B040` → `sub_18002B350`）を読んだ: 画面の囲みの四角が重なり、多角形の辺の交点と相手の中の頂点で奥行きの差が 1e-12 を超えれば辺を作る。つまり少しでも重なれば順番が決まる。辺がないのは重ならない対だけで、その順は AE のたどり方しだい（縁のぼかしで同じ画素を共有しうる）→ (c) の「余白の帯」はこのため。最初は重なりの面積 64 px² 未満もあいまいにしていたが、この解析で 0.01 px² 未満に改めた（380 枚で組 35 枚のまま、100 枚で 58 → 67 枚）。
