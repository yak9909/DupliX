## 2. 事前調査で分かったこと（Web・SDK ガイド）

- エフェクトの出力は 2D の RGBA のみで、Z は持てない。
- 描画中に `AEGP_RenderAndCheckoutLayerFrame` を使うと、無限ループになりうると公式ガイドが警告している。
- エフェクトが AEGP で外部の情報を読んでも、AE はその依存を知らない（キャッシュが更新されない）。
- SDK サンプル `SmartyPants` は、PreRender で AEGP の値を読み、`GuidMixInPtr` でキャッシュのキーに混ぜる方法を示している（将来の「上限なし」対応の手がかり）。
- `AEGP_GetEffectCamera` は描画中に動かないという報告がある。
- Trapcode Particular の Obscuration Layer は同系統の手法だが、対象は指定したレイヤーだけで、半透明に非対応、縁にアンチエイリアスがない。
- AE の 3D レンダラーの内部名: `ADBE Advanced 3d` ＝クラシック 3D、`ADBE Calder` ＝ Advanced 3D、`ADBE Ernst` ＝ Cinema 4D。

### 5.1 クラッシュ修復ダイアログと、画面に出さない実行（2026-11-23）

**ダイアログの正体**
- AE を強制終了すると、次の起動で「クラッシュ修復オプション」が出る（[セーフモードで開始] [環境設定をリセット] [プラグインを管理] [続行（既定）]）。モーダルで、`-r` のスクリプトはその後ろで待つ。「続行」で閉じれば、スクリプトはそのまま実行される。
- ウィンドウはタイトルが空の `#32770`（523×348）で、中身は独自描画（DroverLord）のため、UI Automation では文字もボタンも見えない。

**AE がクラッシュを判定する仕組み（レジストリの差分で特定）**
- `HKCU\Software\Adobe\After Effects\AppStates\<セッションの GUID>` に、セッションごとの記録がある。
  - `AppState` = 3: 起動中。正常に終了すると 1001 に書き換わる。
  - `ProcessID`: そのセッションの pid（QWORD）。
- 強制終了したセッションは `AppState=3` のまま残る。次の起動で AE がこれを見つけてダイアログを出す。
- `HKCU\Software\Adobe\After Effects\25.6` の `ForceQuitOccured=1` は、正常終了したあとも 1 のままで、判定には使えなかった。

**対策（`spike/tools/ae_guard.ps1` の `Repair-AeCrashState`）**
- 起動の前に、「プロセスがもう存在しないのに `AppState≠1001`」のセッションを 1001 に書き換える。生きている AfterFX のセッション（利用者の AE の可能性がある）には触らない。
- 確認: 強制終了 → 書き換え → 再起動で、ダイアログは出なかった。書き換えずに起動すると出た。通しの `run_s1.ps1` もクラッシュ状態から最後まで通った。
- OCR で画面の文字を読む方式も試したが、誤読が多く不安定なのでやめた（利用者の指示）。

**画面に出さない実行（`spike/tools/ae_bg.ps1`）**
- AE を、見えない別の Win32 デスクトップ（`WinSta0\randamu_bg`）で起動する（`CreateDesktop` ＋ `CreateProcess` の `lpDesktop`）。利用者の画面には何も出ず、フォーカスも奪わない。環境変数も引き継がれる。
- そのデスクトップのウィンドウは `EnumDesktopWindows` で列挙できる。`PrintWindow` で AE のウィンドウだけを撮影できる（利用者の画面は写らない）。
- 終了: ホーム画面（大きな DroverLord ウィンドウ）があると WM_CLOSE が無視される。Escape をホーム画面に送ってから、メインウィンドウ（クラス `AE_CApplication_25.6`）に WM_CLOSE を送る。読み込み中も無視されるので、効くまで繰り返す（`Stop-AeHidden`）。
- すでに AfterFX が起動していると、`-r` のスクリプトはそちらに渡ってしまう。`run_s1.ps1` は、AfterFX が動いていたら止まる。

**ネットで見つかった先行例（11/23 調査）**
- nexrender（オープンソース）は、AE に付属する `commandLineRenderer.jsx` を書き換えて、UI のない aerender でもスクリプトを実行できるようにしている。ただし Program Files 内のファイルの書き換え（管理者権限）が必要。AE 2025 の aerender では `-r` が「Illegal argument flag」になるという報告もある。
- クラッシュ修復ダイアログについては、`-noerr` を付けると出なくなるという利用者の報告が 1 件ある（未検証）。

## 6. 実験 S1: 出力をコンプ座標に合わせる

**方法**
- 200×200 の 2D 平面にエフェクトを適用した。
- 自レイヤーの変換は、エクスプレッション付きの POINT_3D パラメータで受け取った（`toComp([0,0])`、`toComp([100,0])`、`toComp([0,100])`）。そこからアフィン変換を作り、出力範囲（レイヤー座標）をコンプ全体に広げた。使ったのは SmartFX の `result_rect` / `max_result_rect` と `PF_RenderOutputFlag_RETURNS_EXTRA_PIXELS`。
- コンプ座標の (100〜300) に赤い四角、コンプの縁に 8px の緑の枠を描いた。

**結果: 合格（4 種とも）**
- 変換なし、移動・縮小 50%・回転 30°、アンカー変更・拡大 150%/120%、対象を奥へ移動、の 4 種。
- 出力ワールドの `origin_x/origin_y` は、返した `result_rect` の左上と一致した（例: 変換なしで 1920×1082、原点 (-860,-441)）。
- AE が要求してくる `output_request.rect` は、コンプより広めの範囲だった。
- 回転・拡大したレイヤーでは、AE がエフェクトの出力をレイヤーの変換で再サンプリングするので、縁が 1px ほどにじむ（判定は ±1px で許容）。
- 実装上の注意: SmartRender では、`checkout_output` の前に入力を 1 つ以上チェックアウトする必要がある。逆順だとエラー 516 になる。

## 7. 実験 S2: レイヤースロットと他レイヤーの情報

**方法**
- `PF_Param_LAYER` を 64 個定義した。
- スロット 1 に 400×300 の 3D 平面（Target）を入れた。
- エクスプレッションで Target の角の画面座標と深度を取得した:
  ```
  var L = effect('RandamuSpike')('Slot 1');
  var p = L.toComp([u, v, 0]);
  var z = thisComp.activeCamera.fromWorld(L.toWorld([u, v, 0]))[2];
  [p[0], p[1], z]
  ```

**分かったこと**
- 64 個のレイヤーパラメータを定義できた（ParamsSetup が成功し、パラメータは合計 72 個）。
- エクスプレッションから、エフェクト自身のレイヤーパラメータ経由でレイヤーを参照できた。
- `toComp()` は 3D レイヤーについて、カメラ投影後の画面座標を返した。Target を Z=800 に下げると、画面上で小さく中心寄りになった。
- カメラ空間の深度も取れた（例: 2896〜2929）。
- チェックアウトの結果: 対象は `ref 400x300`、`max_result_rect (0,0,400,300)`、`solid=1`。空のスロットは 0×0 で、エラーにならない。
- 画素は、レイヤー座標（変換なし）で取れた（中心の画素 = Target の色 (0.102, 0.400, 0.902)）。

**形の一致**
- 1 回目: 3 つの角からアフィンで延長していたため、右下にはみ出した。このカメラでは Target が斜めに写る（透視）ため。透視補正つきの対応づけ（1/z、u/z、v/z を画面座標の 1 次式として 3 つの角から解く）に変えた。
- 判定方法も変えた。AE は合成を線形の色で行うようで、色の計算で比べると合わない。そこで、エフェクトを無効にした同じコンプ（＝ AE が描いた正解）を一緒にレンダーし、シルエットの IoU で比べる方式にした（`spike/tools/check_s1.py`）。
- 2 回目: 判定で「こちらの重ね描きが 0 画素」になった。原因は下の 8 節（キャッシュ）。
- 3 回目以降: AE の自動実行の問題（5 節の最後の 2 行）で止まっていた。
- 11/23: **合格（4 種とも）**。IoU は 0.9899〜0.9939。食い違う画素はすべて相手の形の縁から 2px 以内で、上下左右に均等に散っている（位置ずれではなく、輪郭のアンチエイリアスと、拡大したレイヤーの再サンプリングによる縁の削れ）。外形の範囲は正解と同じ。
- 判定を変えた: IoU の固定のしきい値（0.99）ではなく、「食い違う画素がすべて相手の形の縁から 2px 以内（両方向）かつ IoU > 0.97」。形を 2px ずらすと必ず不合格になることを確かめた（拡大したレイヤーでは 1px でも不合格）。

## 7.1 実験 S2b: レイヤーの種類ごとのチェックアウト結果（2026-11-23）

**方法**: Slot 1 の対象を、平面以外の 3D レイヤーに替えたコンプを 8 つ足した（`make_s1.jsx` の `t_*`）。対象はすべて位置 (1300, 500, 0)、カメラは同じ。プラグインのログに、チェックアウトした画素の不透明部分の数と範囲（バッファ座標＋origin）を出し、AE 自身が描いた正解の形と比べた。

| 対象 | チェックアウトの結果 | 正解との一致 |
|---|---|---|
| PNG（穴あきの円、300×300） | レイヤー座標の素材そのもの（300×300、origin 0） | 合格（IoU 0.988） |
| プリコンプ（コラップスなし） | レイヤー座標のプリコンプの絵（400×300） | 合格（IoU 0.982） |
| テキスト | **コンプ座標の、3D 変換とカメラ投影を済ませた絵**（バッファ 2304×1296、origin (-192,-108)、不透明部分 L1175 T427 R1316 B494） | 範囲は正解（L1174 T425 R1317 B495）と 1〜2px で一致。今の「平面として対応づける」処理では 0 画素 |
| シェイプ | 同上（不透明部分 L1097 T345 R1415 B610 ／ 正解 L1096 T344 R1416 B611） | 同上 |
| コラップスしたプリコンプ | 同上。バッファ自体が画面上の範囲（399×276、origin (1082,362)）で返る | 同上 |
| マスク付きの平面 | **マスクが掛かっていない**平面（`solid=1`） | 不一致（マスクの外も隠してしまう） |
| エフェクト（トランスフォームで内容を 100px 移動）付きの平面 | **エフェクトが掛かっていない**平面 | 不一致 |
| トラックマット付きの平面 | **マットが掛かっていない**平面 | 不一致 |

- マスク・エフェクト・トラックマット付きの 3 つは、ビルドを変えても描画処理が呼ばれず、v0（ただの平面）のキャッシュが使われた。AE 自身が「チェックアウトの結果は同じ」と扱っている。
- AE の UI では、レイヤーパラメータに「ソース／マスク／エフェクトとマスク」の切り替えがある。既定は「ソース」のようだ。SDK（`PF_LayerDef`）にもスクリプトにも、これを設定する手段はない。コミュニティでは「切り替えを設定した状態の効果プリセット（.ffx）を保存して適用する」のが唯一の回避策とされている（未検証）。トラックマットはコンプでの合成なので、この切り替えでも含まれないはず。
- 設計への影響（利用者と相談する）:
  1. 通常のレイヤー（平面・素材・プリコンプ）のマスク・エフェクト・トラックマットが、深度テストに反映されない。
  2. テキスト・シェイプ・コラップスしたレイヤーは、コンプ座標で返るので、平面として対応づける処理は不要（画素はそのまま使い、深度だけ平面の式から求める）。どちらの形で返ったかを、プラグインが判別する方法が要る。

## 7.2 実験 S5: AEGP で他レイヤーを描画させる（2026-11-23）

**方法**
- `RandamuSpike` に追加した。GlobalSetup で `AEGP_RegisterWithAEGP` を呼んでプラグイン ID を得る（成功。ID=57）。
- 自レイヤーの親コンプから「Target」という名前のレイヤーを探し（`AEGP_GetLayerName` が空なら、ソース名で照合する。名前を付けて作った平面はソース名しか持たない）、`AEGP_LayerRenderOptionsSuite2::AEGP_NewFromLayer` → `SetTime`／`SetTimeStep`／`SetWorldType`／`SetDownsampleFactor` → `AEGP_RenderSuite5::AEGP_RenderAndCheckoutLayerFrame` で描画させた。
- 描画する場所を環境変数で切り替えた。`pre` = PreRender で描画して受け取りを pre_render_data に持ち、SmartRender で使い、削除時に `AEGP_CheckinFrame`。`smart` = SmartRender で描画。
- キャッシュ: `pre` では受け取りの GUID（`AEGP_GetReceiptGuid`、16 バイト）を `GuidMixInPtr` に混ぜた。`smart` ではレイヤー ID とコンプ名だけを混ぜた。さらに実行ごとの salt（環境変数）を混ぜ、前の実行のディスクキャッシュを使わせないようにした。
- 平面の対応づけ（S2 の Slot 1 のエクスプレッションと透視補正）はそのままで、画素の出どころだけを AEGP に替えた。判定は S2 と同じ（正解コンプとの形の一致）。

**結果**（`pre`／`smart` × MFR オン／オフの 4 通りで同じ結果。ログは `spike/logs/s5_*.out.txt` と `s5_*.plugin.log`）

| 対象 | AEGP の描画結果 | 正解との一致 |
|---|---|---|
| 平面（v0〜v3） | レイヤー座標の 400×300 | 合格（IoU 0.990〜0.994） |
| PNG・プリコンプ | レイヤー座標 | 合格（0.988／0.982） |
| **マスク付きの平面** | **マスクが掛かった**レイヤー座標の絵 | **合格**（0.987） |
| テキスト・シェイプ | **コンプ座標の、3D 変換とカメラ投影を済ませた絵**（バッファ 1920×1080、rendered region (0,0)-(1920,1080)） | コンプ座標のまま使えば合格（シェイプ 0.985。テキストは細い字なので IoU 0.877 だが、食い違いはすべて縁から 2px 以内） |
| エフェクト付き（トランスフォームで内容を右へ 100px） | エフェクトは掛かるが、**レイヤー本来の範囲（400×300）で切られる**（rendered region L98 T0 R400 B300） | 不合格（IoU 0.757。はみ出した右側 100px が欠ける） |
| トラックマット付き | **マットが掛かっていない**平面 | 不合格（予想どおり。マットはコンプでの合成で掛かる） |
| コラップスしたプリコンプ | 描画は成功（err 0）するが、**world が NULL** | 画素が取れない |

- **再入・デッドロック**: なし。PreRender からも SmartRender からも呼べた。MFR オンでは複数の描画スレッドから同時に呼ばれたが問題なかった。aerender でも動く。1 回の描画は 0.3〜40ms（初回が遅く、2 回目以降は AE のキャッシュで 0.3ms 程度）。
- **時刻**: `NewFromLayer` の既定の時刻は 0（テストのコンプはすべて 0 秒なので、`SetTime` にコンプ時間とレイヤー時間のどちらを渡すべきかは未確認）。
- **キャッシュ**: `pre` で受け取りの GUID を混ぜると、12 コンプすべてで描画処理が呼ばれた（S2b では t_mask などが v0 のキャッシュを再利用していた）。同じコンプ・同じ時刻では GUID は同じ値で安定していた。対象を変えたときに再描画されるか（S4）は未確認。
- **クラッシュ**: コラップスしたレイヤーの受け取り（world が NULL）に `AEGP_GetRenderedRegion` を呼ぶと AE が落ちる。world が NULL のときは受け取りに触らないようにして解決した。
- PreRender は 1 フレームで 3 回呼ばれ、そのたびに描画している（2 回目以降は AE のキャッシュから速く返る）。
- キャッシュの判定で意味があるのは `pre` の結果だけ。`smart` ではコンプ名を混ぜたので、コンプごとに描画されたのは当然で、内容による判定の証拠にならない。
- **受け取りの GUID が拾うのは対象の中身の変化だけとみられる**。平面・素材・プリコンプはレイヤー座標で描画されるので、対象を動かす・回す・カメラを変えても、画素も GUID もおそらく変わらない。今それを拾っているのは、角の位置を受け取るエクスプレッション付きのパラメータ。位置の取得も AEGP（`AEGP_GetLayerToWorldXform`＋カメラ）に移すなら、変換・カメラ・コンプのレイヤー一覧も自分で GUID に混ぜる必要がある（S5b の候補）。
- **コラップスしたプリコンプ**: AEGP では画素が返らないが、スロット（`PF_Param_LAYER`）のチェックアウトはコンプ座標の投影済みの絵を返す（S2b）。world が NULL のときにスロットの絵をコンプ座標として使うと合格した（IoU 0.9912、食い違いはすべて縁から 2px 以内）。ただし、スロットは「ソース」扱いなので、コラップスしたレイヤー自身に掛けたマスク・エフェクトは入らない見込み（未確認）。また 64 スロットの仕組みに頼る。
- `Remove-AeEffectCrashRecord` は、手で作った UTF-16 ビッグエンディアンの見本（自分の記録とほかのプラグインの記録）で、自分の記録だけを消すことを確かめた。実物のクラッシュ記録ではまだ試していない（実物は起動時に消費済みだった）。

**エフェクトによるクラッシュの記録（自動テストの注意）**
- AE がエフェクトの中で落ちると、`%APPDATA%\Adobe\After Effects\25.6\Effect Crashed.txt`（UTF-16 ビッグエンディアン、BOM なし。中身は「Crashed Effect File Version 1.1」とエフェクトの照合名・表示名）が書かれる。次の起動で AE がこれを読んで消し、「『RandamuSpike』が原因で After Effects が終了した可能性があります」（492×295、［エフェクトを無効にする］［有効のままにする］）を出す。モーダルなので `-r` のスクリプトが止まる。
- 1 回出すと記録は消えるので、出たあとで探しても見つからない。クラッシュ直後（AE を起動する前）の状態とレンダー前の状態の差分で特定した（`run_s1.ps1` がクラッシュ時に `crash_state` に保存する）。
- 対策: `ae_guard.ps1` の `Remove-AeEffectCrashRecord`（`Repair-AeCrashState` から呼ぶ）が、起動前に**自分のエフェクトの名前を含む記録だけ**を消す。ほかのプラグインの記録は残す。
- aerender は、ホストの AE が落ちても終了コード 0 を返すことがある（出力に「Unable to receive」）。`run_s1.ps1` はこの文言を見て警告する。

## 7.3 実験 S5c: はみ出すエフェクトのために描画範囲（ROI）を広げる（2026-11-23）

**調べたこと**
- 実行時に、スイートの版を 1〜20 まで取得してみた（`ProbeSuiteVersions`）。レイヤー用の描画オプションは v1・v2 だけで、ヘッダにない新しい版はない。関数表はすべて `Support Files\Required\AEGPDriver.aex` にある。
- `AEGP_GetROI`（AE_GeneralPlug.h 3612 行）は 3D レンダラー（Artisan）用で、使えない。
- IDA（idalib）で `AEGPDriver.aex` の `AEGP_NewFromLayer`（RVA 0x4f130）を読んだ。
  - `AEGP_LayerRenderOptionsH` の中身は、AE 内部の C++ オブジェクト `BEE_LayerRenderOptions*` そのもの。
  - 既定の範囲は、`BEE_Layer::GetFullRect` をレイヤー→コンプの 2D 行列で変換した矩形で、`BEE_RenderOptions::SetROI(const M_Rect&)` で設定している。**この関数は `BEE.dll` から名前つきで公開されている**（`?SetROI@BEE_RenderOptions@@QEAAXAEBUM_Rect@@@Z`、取得用は `?GetROI@BEE_RenderOptions@@QEBAAEBUM_Rect@@XZ`）。
  - `M_Rect` は 16 ビット整数 4 つで、並びは `{top, left, bottom, right}`（アイテム用の `AEGP_SetRegionOfInterest`／`GetRegionOfInterest` の実装から確認）。
- 実験コード: `NewFromLayer` のあとで、読み込み済みのモジュールから上の 2 つを `GetProcAddress` で探し、ROI を読み、広げて設定し直す（`ApplyRoiExperiment`。環境変数 `RANDAMU_S5C_ROI` = `margin:N`／`zero`）。

**結果**（すべて `pre`。`margin:30000` は MFR オン／オフの両方）

| ROI | 結果 |
|---|---|
| 既定 | コンプ座標の矩形（例: 位置 (1300,500) の 400×300 → T350 L1100 B650 R1500）。3D の投影は考慮されない |
| `margin:200` | **t_effect が合格**（IoU 0.757 → 0.9938）。受け取りは 404×304、rendered region L98 T-2 R502 B302（エフェクトの結果がある範囲だけ。ROI 全体ではない）。既存の原点の処理（範囲と world の大きさが一致すれば範囲の左上が原点）で正しく対応づく。ほかの項目は前と同じ |
| `zero`（{0,0,0,0}） | 何も描画されない（レイヤー用では「空」の意味。アイテム用の「全部」とは違う）。不可 |
| `margin:30000`（±約 3 万） | t_effect 合格（0.9938）。さらに**コラップスしたプリコンプが AEGP で画素を返すようになった**（今までは world が NULL）。コンプ座標の投影済みの絵（399×276、原点 (1082,362)）で、コンプ座標として扱うと合格（IoU 0.9912、MFR オン／オフとも） |

- 不合格のまま: t_matte（トラックマット。次の実験）、t_text（IoU 0.877。細い字のため。食い違いはすべて縁から 2px 以内で、前と同じ）。
- コラップスの判定は `AEGP_GetLayerFlags` の `AEGP_LayerFlag_COLLAPSE`。テキストもこのフラグが立っている（どちらもコンプ座標で返るので、扱いは同じでよい）。
- `margin:200` ではコラップスは world が NULL のままだった。理由は未調査（投影後の範囲は ROI の中に入っていた）。
- 再入・デッドロック・クラッシュはなし。

**追加の確認（同日）**
- 内部の既定値: `LayerStage=3`、`LayerRenderType=2`、`EffectsToRender=-1`（`BEE.dll` の公開の Get 関数で読んだ）。`SetLayerStage` で 4・5 にしても、トラックマットは掛からなかった（絵は平面のまま）。
- `margin:200` と既定ではコラップスが NULL、巨大な範囲では画素が返る。助言役の仮説: AE は ROI をレイヤー自身の座標（0〜400 程度）に戻してから、コンプ座標の出力（1082〜1481）と交差させているのかもしれない。そうなら「表示範囲の逆投影＋余白」で上限を決めると、コラップスがまた取れなくなる。上限を設計するときに確かめる。

**本番への注意（未解決）**
- 公開されていない C++ の関数（名前の装飾つき）に頼る。AE の版が変わると名前や `M_Rect` の形が変わるおそれがある。見つからないときは既定の範囲に戻す（制限として扱う）こと。起動時に `GetROI` で読めた値が既定の範囲と合うかを確かめる安全策も考えられる。
- 範囲は 16 ビット（±32767）。巨大な ROI でも、AE はエフェクトの結果がある範囲だけを描画する。ただし結果の範囲が非常に大きいエフェクト（タイル系など）では、受け取りが巨大になりうる。本番では「コンプの表示範囲を対象の平面に逆投影した範囲＋余白」などで上限を決める案を検討する。

## 7.4 実験 S6: トラックマットを自前で掛ける（案 A、2026-11-23）

**方法**
- PreRender で `AEGP_GetTrackMatteLayer`／`AEGP_GetLayerTransferMode` から、マットのレイヤーと種類を取る。マットのレイヤーも S5c と同じ方法（ROI 拡大つき）で AEGP に描画させる。
- SmartRender で、コンプ座標の各点について「Target のアルファ × マットの値」を求める。マットの値は種類ごとに、アルファ／1−アルファ／ルミナンス／1−ルミナンス。
- テストのコンプ: `t_matte`（平面、アルファ）、`t_matte_inv`（反転アルファ）、`t_matte_luma`／`t_matte_nluma`（白と黒の不透明な四角を並べたシェイプ。アルファとルミナンスで結果が変わる）。

**結果**: **4 種とも合格**（`render=aegp`。IoU 0.9827〜0.9915、食い違いはすべて縁から 2px 以内）。v0〜v3・t_mask・t_effect・t_collapse なども崩れず、全項目が合格（ALL OK）。
- マットのレイヤーはビデオがオフ（`videoActive=0`）でも、AEGP で画素を返す（平面 250×250 で 62500 px すべて不透明）。
- 種類の値は `mode=1` アルファ、`2` 反転アルファ、`3` ルミナンス、`4` 反転ルミナンス（ログの `S6 matte:`）。
- マットのレイヤー自身にマットがある場合（入れ子）や、マットに変換・エフェクトのアニメーションがある場合は未確認。

**シーン生成の不具合（同日に解決）**: 出力モジュールが 30 個を超えると、日本語名のテンプレート（「TIFF シーケンス (アルファ付き)」）の名前が化けて適用できなくなる。`getSettings`／`setSettings` で写す方式は形式が写らず、2 個目以降が既定の「def」（H.264）のままだった。1 個目に適用したあと `saveAsTemplate("RNDM_TIFF_A")` で ASCII 名のテンプレートとして保存し、2 個目以降はその名前で適用する方式で解決した（利用者の AE の出力テンプレートに `RNDM_TIFF_A` が 1 つ増える）。

## 7.5 実験 S4・S5b: 変更で再描画されるか／位置を AEGP で取る（2026-11-23 午後）

**方法**
- aerender は毎回別のプロセスで、ディスクキャッシュも「読み取り専用」なので、古い絵が返ることがない。そのため、AE 本体の中で「描く → 変える → 描く」を行う（`scenes/make_s4.jsx`、`tools/run_s4.ps1`、`tools/check_s4.py`）。`s1.aep` を開き、各ケースで変更前（`_a`）と変更後（`_b`）を、正解用の `_ref` コンプにも同じ変更を加えて `renderQueue.render()` で描く。
- スクリプトはプラグインのログに `== step <名前>` を書き込む。区切りごとに SmartRender の回数（0 回 = キャッシュから返った）を数える。
- ケース: マスクの形、エフェクトの値、プリコンプの中のレイヤー、マットのマスク（ここまでは受け取りの GUID でしか気づけない）、不透明度 0、対象の移動、カメラの移動。

**段階 0（試験が意味を持つかの確認）**: 変更なしで同じコンプを 2 回描くと、2 回目は SmartRender 0 回（キャッシュから返る。PreRender は 1 回呼ばれる）。合格。

**結果**

| 条件 | 結果 |
|---|---|
| 今の方式（スロット＋エクスプレッション＋受け取りの GUID） | 不透明度 0 以外はすべて再描画されて正解と一致 |
| 対照: 対象の受け取りの GUID を混ぜない（`-NoGuid`） | マスクとエフェクトの変更が**古い絵のまま**（SmartRender 0 回）。試験が失敗を検出できることを確認。プリコンプの中身は、スロットのチェックアウトの依存で再描画された |
| S5b: 位置を AEGP で計算（`-S5b 1`、エクスプレッションを外す） | 全ケースで再描画されて一致 |
| S5b＋スロットも空（`-S5b 1 -NoSlot`、本番に近い条件） | 全ケースで一致（不透明度の対処後は不透明度 0 も合格） |
| 対照: S5b＋スロットなし＋計算値を鍵に混ぜない（`-NoMix`） | 自分のレイヤーの変形だけが違うコンプ（v1_moved、v2_anchor）で、**別のコンプのキャッシュが流用された**（変更前の絵が間違い、SmartRender 0 回）。計算値を鍵に混ぜることは必要 |

**不透明度**: AEGP の描画結果には、レイヤー自身の不透明度が入らない（トラックマットと同じく合成の段階で掛かる）。`AEGP_StreamSuite6` で対象とマットの不透明度を読み（`AEGP_LayerStream_OPACITY`、エクスプレッション適用後）、自前で掛けて鍵にも混ぜる方式で解決（不透明度 0 で重ね絵が消える。途中の値は形の判定では確かめていない）。

**S5b: 位置とカメラを AEGP で計算する**
- 自分・対象・マットのレイヤーの点 (0,0)・(100,0)・(0,100) を、`AEGP_GetLayerToWorldXform` でワールド座標に移し、`AEGP_GetEffectCameraMatrix` の逆行列でカメラ空間に移して、`x·dist/z + 幅/2` で投影する（行列は行ベクトル `p' = [x y z 1]·M`）。2D レイヤーはワールド座標 = コンプ座標。`AEGP_GetEffectCamera` 系は SDK の説明では FRAME_SETUP／RENDER 用だが、SmartFX の PreRender でもエラーなく動いた。
- エクスプレッションの値との差は、全 15 コンプで**小数第 4 位まで 0**（2D の自分のレイヤーの z だけ違うが、使っていない）。S1 の全項目も合格（`RANDAMU_S5B=1`）。
- 計算は 1 回平均 0.6ms。

**速さ（重要）**: エクスプレッション付きの点パラメータ 10 個のチェックアウトに、各フレームの最初の PreRender で **300〜690ms** かかっていた（同じフレームの 2 回目以降は 0.2ms）。S5b ではこれがなくなる。AE は 1 フレームで PreRender を 3 回呼び、そのたびに AEGP 描画が走るが、**AEGP の描画（準備を含む）は 1 フレームあたり合計 3〜13ms**（対象 1 つ、マットありで 2 つ。新しい中身の初回は 1 回 10ms 前後、2 回目以降は約 1ms）。PreRender の合計として測った 60〜100ms の大半は、実験用のログの書き込み（1 行ごとにファイルを開く）と、画素を全部数えるログ処理で、本番にはない。

**表示されないレイヤー・カメラなし（同日、S1 に追加）**
- AEGP の描画は、目のスイッチがオフのレイヤーや、時間の範囲外のレイヤーでも画素を返す。そのままだと、AE が描かないレイヤーが隠れの原因になる。`AEGP_IsVideoActive`（コンプ時間）が偽なら不透明度 0 として扱う方式で解決（`t_hidden`、`t_outrange` が合格。どちらも `videoActive=0` になる）。マットのレイヤーはビデオがオフでも使われるので、この判定はしない。
- カメラのないコンプ（`t_nocam`、対象は z=500）でも、`GetEffectCameraMatrix` は AE の既定のカメラを返し、合格（IoU 0.9970）。行列の位置の値は、カメラレイヤーがあるとき (0,0,-2666.67)、ないとき (960,540,-2666.67) で座標の原点の取り方が違うが、どちらも正しく投影できた。
- **スロットもエクスプレッションも設定しないシーン**（`make_s1.jsx` を `RANDAMU_S1_NOSLOT=1` で生成、`RANDAMU_S5B=1`）で、**S1 の全 18 項目が合格**。

**まだ確かめていないこと**
- 合成の段階で掛かる、ほかの性質: 調整レイヤー（対象より上）、描画モード、レイヤースタイル、ソロ。不透明度・トラックマット・表示状態は対処済み。
- 画面のプレビュー（コンポジションパネル）での挙動。今回はレンダーキューで確かめた。
- レイヤーの追加・削除・並べ替え（本番では全レイヤーが対象なので、レイヤー一覧も鍵に混ぜる必要がある見込み）。
- 時間の扱い: `AEGP_SetTime` に渡す時間が、コンプ時間かレイヤー時間か（テストのレイヤーはすべて 0 秒から始まる）。
- MFR のオン／オフ（AE 本体の設定のまま）。

## 7.6 実験 S7: 全レイヤーを対象にする（2026-11-23 夕方）

利用者の決定（スロットとエクスプレッションをやめ、すべて AEGP で取る）を受けて、名前で選んだ「Target」1 枚ではなく、コンプの全レイヤーを対象にした（`RANDAMU_S7=1`。重ね絵は全対象の和集合）。

**対象に入れるかの規則**（`SkipReason`。理由はログの `S7 layer N 'name': skip (...)`）
- 自分自身／カメラ・ライトなど描画しない種類（`AEGP_ObjectType` が AV・テキスト・シェイプ以外）／ヌル（`AEGP_LayerFlag_NULL_LAYER`）／ガイド（`GUIDE_LAYER`）／調整レイヤー（`ADJUSTMENT_LAYER`）／ソロのレイヤーがあるときのソロでないレイヤー（`SOLO`。`IsVideoActive` はソロを考慮しないので自前で判定）／`IsVideoActive` が偽（目のスイッチ・時間の範囲。マットの元レイヤーもここで外れる）／このエフェクトを持つレイヤー（`AEGP_EffectSuite5` でマッチ名を比べる）／実験用の `BG`（名前で除外。結論には使わない）。
- 再入の防止: このエフェクトを持つレイヤーを外すうえで、さらに「同じスレッドでの入れ子（thread_local）」と「同じレイヤー・同じ時間の処理が実行中（全体の集合）」を検出したら対象 0 枚で返す。ただし、この防止策が実際に働く場面（別のエフェクトがこちらのレイヤーをエフェクト込みで取り込む場合）はまだ作れておらず、試していない。

**キャッシュの鍵**: 対象ごとに、受け取りの GUID、レイヤー ID と並び順、位置の 3 点、不透明度、マットの種類と位置とその受け取りの GUID を混ぜる。最後に自分の位置と対象の数を混ぜる。

**結果**
- S1（スロットもエクスプレッションもないシーン、24 項目）: **全合格**。新しく足したもの: `t_null`・`t_guide`・`t_adjust`（何も描かない）、`t_solo`（ソロの `Other` だけが対象）、`t_two_fx`（エフェクトが 2 つ。止まらず、落ちず、互いに対象から外れる）。
  - 対象 0 枚で自分の位置も同じコンプは、AE がキャッシュを 1 つにまとめて使い回す（出力が同じなので正しい）。
  - 最初の `t_solo` の不合格は、試験用のシーンで `Other` がエフェクトのレイヤーより上にあり、重ね絵を覆ったため（「エフェクトのレイヤーを最上段に置く」前提どおり）。シーンを直して合格。
- S4（`-S7 -S5b 1`）: 従来の 7 ケースに加え、**表示の切り替え（hide）・追加（add）・削除（delete）・並べ替え（reorder）・49 枚（many）がすべて合格**。削除のあとは、追加する前と同じ状態のキャッシュが正しく使われた（SmartRender 0 回、絵は正しい）。many は細い文字のコンプを使ったので、S1 と同じく IoU の下限 0.80（縁から 2px の規則は同じ）で判定した。
- **速さ（49 枚）**: AEGP の描画は 1 フレームあたり描画 143ms＋準備 162ms（PreRender 3 回分、計 147 回、1 回あたり約 2ms。準備の時間には実験用のログの書き込みを含む）。本番では、同じフレームで 3 回呼ばれる PreRender の結果を使い回して減らす。SmartRender の時間は、Debug ビルドで全画素×全対象を素朴に回しているので製品の目安にならない（本番は対象ごとの投影範囲に絞る）。
- 文字やシェイプのようにコンプ全体の大きさで返る絵では、ログの全画素の走査に 1 秒以上かかる（AEGP の描画そのものは 50ms 程度）。

**本番への注意**
- 入れ子のプリコンプの中にもこのエフェクトがある場合、thread_local の検出が働いて、中のエフェクトが対象 0 枚になる（安全側だが結果は不完全）。本番では検出の仕方を詰める。
- 音声だけのレイヤーは試していない（`IsVideoActive` で外れる見込み）。

## 8. 重要な発見: AE のディスクキャッシュ

- プラグインを作り直したのに、出力が前回とまったく同じだった。
- プラグインのログを見ると、PreRender / SmartRender が一度も呼ばれていなかった。
- AE（aerender を含む）のディスクキャッシュは、プロセスをまたいで残る。パラメータが同じなら、プラグインのバイナリが変わっても古い結果を返す。
- 対策: `PF_OutFlag2_I_MIX_GUID_DEPENDENCIES` を立てる（PiPL の OutFlags_2 も 0x08201400 に更新）。PreRender で、ビルドごとの識別子（`__DATE__ " " __TIME__`）を `GuidMixInPtr` に混ぜる。11/23 に**効果を確認**（ビルドを変えると描画処理が呼ばれる）。
- 注意: 同じビルドで、入力が AE から見て同じなら、別のコンプでもキャッシュが共有される（7.1 節のマスク付きの平面などが、ただの平面の結果を再利用した）。
- 実行スクリプトに「SmartRender の呼び出し回数」の確認を足した。0 回ならキャッシュから返されたと警告する。
- 本番とホットリロードにも、同じ仕組みが必要。
